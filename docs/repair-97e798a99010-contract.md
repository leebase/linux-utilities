# Problem

In governed run `97e798a99010`, preserved in sealed evidence directory `/home/lee/projects/linux-utilities-agent-orch-runs/97e798a99010`, execution failed during worker startup and preflight validation with the following failure message:
`Worker exited with non-zero code 1: Smoke check did not pass before startup timeout.`

Analysis of the failure and environmental root causes:

1. **Smoke Check Startup Window vs. Heavy Execution Workloads:**
   The Agent-Orch smoke runner relies on `tests/smoke_manifest.json` to manage worker process startup and health verification. The manifest declares startup and check parameters, including `start_command` (`python3 tests/smoke_start.py`), `check_command` (`python3 tests/check_sysdiff_smoke.py`), `startup_timeout_seconds: 10`, `poll_interval_seconds: 0.25`, and `check_timeout_seconds: 300`. In run `97e798a99010`, the orchestrator launched a worker process and polled for smoke readiness. The smoke check did not complete and report success within the 10-second `startup_timeout_seconds` window, causing the orchestrator watchdog to abort the worker and report a non-zero exit code 1.

2. **Coupling of Smoke Verification to Full Test Suite Execution:**
   In the repository's current architecture, `tests/check_sysdiff_smoke.py` invokes `bash scripts/smoke.sh`, which executes `make test`. In the project `Makefile`, the `test` target delegates directly to `test-suite`, which rebuilds the C binary `build/sysdiff`, runs shell fixture tests (`./tests/test_sysdiff.sh`), and then executes the full pytest suite (`pytest tests/ -q`) across hundreds of test cases spanning unit, integration, and fuzzing tests. On loaded runners, resource-constrained container environments, or during cold compiler caches, executing compilation, shell fixtures, and pytest collection and test execution can easily exceed the tight 10-second `startup_timeout_seconds` limit. When the smoke check does not succeed before the startup timeout expires, the smoke runner treats the worker as unresponsive or broken, terminating execution fail-closed.

3. **Need for Startup Timeout Hardening and Execution Bounding:**
   To resolve this failure, the repair must ensure that smoke verification adheres strictly to startup timeout constraints. Startup preflight and smoke verification procedures must be decoupled or optimized so that initial startup verification confirms basic worker readiness and binary functionality rapidly (well within the 10-second startup timeout), while allowing comprehensive quality and regression suites to execute under their allocated full-check timeout budgets (`check_timeout_seconds: 300`). This ensures that worker processes pass startup checks predictably without triggering watchdog timeouts or non-zero exit code 1 aborts.
